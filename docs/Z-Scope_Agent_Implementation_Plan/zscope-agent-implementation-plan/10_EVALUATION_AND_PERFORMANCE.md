# 10 · 质量、性能与轻量验证

## 优先级与比较方式

先控制正式报告误报，再提高真实缺陷召回，在同等质量与覆盖下改善性能；项目理解和体验贯穿实现。不要把五项目标合成一个任意权重总分。

原概念设计的 precision ≥98% 仅作为待基线校准的愿景，不是已测成绩或本版固定门槛。第一轮记录现有基线、分类型缺口和误报来源，再与用户确定适用项目的目标值；不能通过零报告或把难题全移入未决达标。

## 指标

| 指标 | 口径 |
|---|---|
| 正式 precision | 独立标注 TP/(TP+FP)，按根因、类别和平台报告；分母为零记 N/A |
| actionable FDR | FP/(TP+FP)；没有安全样本/TN 时不称经典 FPR |
| 最终 recall | 已确认且匹配的真缺陷 / 纳入范围的全部已知真缺陷 |
| 候选 recall | 曾生成对应候选的真缺陷 / 同一 truth 集 |
| 找到后的确认率 | 正确确认的真缺陷 / 已找到的真缺陷 |
| 条件/待验证 | 原因、年龄、影响范围和真缺陷滞留数，不能计入正式 TP |
| 未裁定 U | 数量/比例与抽样方式，不把已审子集 precision 冒充全体 |
| 覆盖 | 目标/编译实例、解析、对象/协议、回调/并发、缺口/延后 |
| 误排除 | 真实缺陷被 ruled_out 的数量、依据与可重核性 |
| 理解项目 | 公共模型解锁义务数、冲突数、复用收益、需要用户补充的次数 |
| 体验 | 首次有效配置耗时、手填字段/重复配置数、夜间阻塞次数、验收定位时间 |

报告 confirmed 与包含 review 的视图，但不能混用分母或将条件性缺陷包装成确认。严重度、可利用性与确认程度分开。

## 数据集与真实性

使用基础缺陷/安全反例、真实项目修复前后、业务资源协议、并发回收、构建变体及增量变更。按项目划分调试与保留样例，避免只对换名 fixture 优化。

Range 保持故意植入的缺陷；不修改它们来让扫描成功。truth 只用于入口预检和扫描后的独立评分，不能进入扫描/Agent/Wiki 上下文。未匹配 truth 的告警需独立判定，不能自动算 FP。

支持范围内解析失败、超时、未决仍影响最终 recall；不得在看到结果后缩小范围。重复报告与根因数分开保存，过度合并不同实例不能美化 precision。

## 性能分解

分别测冷全量、输入不变的复用全量、给定变更的增量；记录环境/构建/模型、CPU/RSS/磁盘、端到端与 scan wall、分阶段耗时、队列、失败重试、LLM 输入输出/缓存 token、复现和求解器成本。

优先优化：全量建模冗余、重复解析/工具查询、公共接口重复补证、无证据增量复判、每个候选重复编译、多个并发池争抢。候选数下降或 tokens 下降不能单独说明有效加速。

用量复用现有 scan-wide ledger，一次物理请求只计一次，嵌套调查不重复归集。时窗截止由 scheduler 停止新工作，剩余项持久化，不能把账本变成偷偷丢候选的过滤器。

## 最小开发验证

每个切片：相关正例+反例、必要集成、实际命令和结果摘要。普通结构/确定性改动先跑相关测试；涉及模型行为才加代表性真实模型任务，涉及动态执行才加真实 sanitizer。失败与 skipped 明示，不全量重跑所有大仓。

模型效果比较用相同输入/配置/模型与可解释尝试次数；小试先一次，发现随机波动或准备比较结论时再重复并报告样本量/范围，不把单次结果写为稳定优势。不预设多级门禁、代码冻结、审批链或固定观察期。

基础消融按需选择：静态 → 项目语义 → 对象盲探索 → 定向验证/复现；或原完整建模 vs 需求建模。每次看新增独占 TP、FP、误排除、未决、覆盖和成本，不要求所有小改动跑完整组合。

## 正式结果与开发结果

开发验证不依赖当前 formal/release 的签名、灰度和 attestation 流程。现有正式协议单独存在；本轮不执行也不修改其历史成绩。

未来清理重流程时，正式协议的代码、CI、说明和状态标识应在专门变更中一起调整；普通本地通过不冒充当前 formal unified/四包发行通过。Linux/WSL、工具健康与答案隔离仍是结果有效性的技术条件。

## 验证记录模板

`工作包 / 输入与环境 / 行为 / 正反例 / 真实命令 / passed-failed-skipped / FP-TP-未决-覆盖 / 时间资源 / 未测项`。

没有真实数据就写“未测”，不填零。对外性能、准确率或平台支持承诺必须指向实际结果；本计划的本轮检查见 [15](15_INDUSTRY_PRACTICES_AND_SOURCES.md)。
