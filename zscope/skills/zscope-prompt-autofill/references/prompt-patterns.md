## 1. 消息分发函数

### 识别特征
- 函数名含 `MsgProc`、`Dispatch`、`Route`
- 主体为 `switch/case` 或函数指针数组分发
- 本身不管理资源生命周期

### 模板
```
这是[模块]层的[消息类型]分发函数，采用[分发方式：switch/case或函数指针数组astMsgProcApi]。请分析：(1)[数组中是否有消息类型重复/switch分支覆盖] (2)[未匹配的消息是否都走到默认处理] (3)每个分支处理完毕后[IPC消息缓冲区/资源]是否被正确释放
```

### 生成规则
- 检测到函数指针数组 → "采用表驱动分发(函数指针数组astMsgProcApi)"
- 检测到 switch/case → "根据消息类型(如XXX_YYY等)将消息路由到对应的处理函数"
- 检测到 DDM_XdlinkMsgFree / DDM_LinkBaseDlinkMsgFree → 添加消息释放检查项
- 检测到嵌套分发(主入口调子分发) → "请求消息的顶层入口，提取消息类型后调用[XxxMsgProc]"

## 2. 资源分配函数

### 识别特征
- 函数名含 `Create`、`Add`、`Alloc`、`Apply`、`Register`、`Bind`、`Connect`、`Join`
- 调用 DDM_ALLOC / malloc 等分配函数
- 资源挂载到全局数据结构(hash表/链表/位图)

### 模板
```
处理[消息类型]。分配[资源类型]资源(通过[分配函数/DDM_ALLOC])，挂载在[全局数据结构]上，在[释放函数1]([条件1])和[释放函数2]([条件2])中被释放。这是跨handler生命周期，[资源类型]不在本函数释放，请不要报告为泄漏。请重点关注：(1)[错误路径回滚] (2)[条件覆盖完整性] (3)[锁保护范围] (4)[悬挂指针风险]
```

### 生成规则
- **必须包含** "这是跨handler生命周期...请不要报告为泄漏" — 这是避免误报的核心声明
- 释放函数需从同模块搜索配对函数名，列出所有触发条件(正常关闭、故障、超时等)
- 错误路径检查项优先级：
  1. 分配后挂载前失败 → 回滚分配
  2. 挂载后响应发送失败 → 回滚挂载+分配
  3. 多步分配(如先分配conn再分配shm) → 前序成功后序失败时的回滚
- 检测到位图操作 → 添加位图分配/释放配对检查
- 检测到引用计数(uiConnCnt等) → 添加计数增减配对检查
- 检测到 rwlock → "rwlock保护范围"
- 检测到 mutex → "mutex保护范围"
- 检测到多把锁 → "加锁顺序(避免死锁)"

### 条件覆盖完整性检查项模板

当检测到全局链表/hash表的节点添加操作，且节点摘除有多个条件时：

```
(2)[资源类型]节点必须在[条件1]和[条件2]两种场景下都被摘除释放，请检查当前代码是否覆盖了所有需要摘除的条件路径，是否存在某种条件下节点永远不会被从[数据结构]摘除导致泄漏
```

## 3. 资源释放函数

### 识别特征
- 函数名含 `Delete`、`Remove`、`Free`、`Release`、`Close`、`Destroy`、`Leave`
- 调用 DDM_FREE / free / close / munmap 等释放函数
- 从全局数据结构中摘除节点

### 模板
```
处理[消息类型]。释放[资源类型]资源([释放函数/DDM_FREE])，从[全局数据结构]移除。这是[配对分配函数]的配对释放handler。请重点关注：(1)[资源不存在时的处理] (2)[链表移除操作的指针更新是否正确] (3)[释放后是否有悬挂指针] (4)[锁保护下的操作完整性]
```

### 生成规则
- **必须包含** "这是[配对分配函数]的配对释放handler" — 让 Agent 理解配对关系
- 从分配函数的 custom_prompt 或同模块搜索获取配对分配函数名
- 检测到链表操作 → "链表移除操作的指针更新是否正确"
- 检测到 hash 表 → "从hash表移除后是否有悬挂指针"
- 检测到位图 → "位图槽位释放(DDM_BitMapUnSet)与DDM_FREE的顺序"
- 检测到双重释放风险 → "重复释放的防护"
- 释放操作顺序检查：先释放位图/计数再释放内存，避免释放后访问

## 4. 故障兜底函数

### 识别特征
- 函数名含 `Fault`、`Error`、`Cleanup`、`Abort`
- 遍历全局数据结构批量释放资源
- 是所有资源生命周期的最终兜底路径

### 模板
```
这是故障安全网函数，当[故障触发条件]时被调用。它遍历全局[数据结构]中属于该[连接/实例]的所有资源([资源类型列表])并批量释放。这是所有资源生命周期的最终兜底释放路径，正常情况下资源应已在[正常释放函数]中释放。请重点关注：(1)遍历[数据结构]时是否遗漏了某种资源类型 (2)[特定资源释放时的关联操作，如引用计数递减] (3)批量释放过程中锁保护是否充分 (4)[嵌套数据结构的释放完整性，如MCM组中成员的释放]
```

### 生成规则
- 列出所有被清理的资源类型 — 从分配函数的 custom_prompt 汇总
- 引用计数相关 → "conn释放时是否正确递减了listen_info的uiConnCnt"
- 嵌套数据结构(如组包含成员列表) → "是否存在只释放了组但遗漏了成员的情况"
- 批量释放的原子性 → "批量释放过程中mutex保护是否充分"

## 5. 只读查询函数

### 识别特征
- 函数名含 `Get`、`Query`、`Info`、`Stat`
- 只读取数据并发送响应，不分配/释放资源
- 不涉及跨handler资源管理

### 模板
```
处理[消息类型]。此函数只读取[信息类型]并发送响应，不涉及跨handler资源管理。请检查：(1)[响应消息构造是否正确] (2)[内存分配失败时的处理]
```

### 生成规则
- 模板简短，2-3条检查项即可
- 不需要"跨handler生命周期"声明
- 重点检查响应构造和分配失败处理

## 6. 初始化/销毁函数

### 识别特征
- 函数名含 `Init`、`Finit`、`Create`/`Destroy`(模块级别)
- 初始化全局mutex、hash表等基础设施
- 销毁时遍历释放所有残留资源

### 初始化模板
```
[模块]资源初始化函数。初始化全局mutex、hash表等。请检查：(1)[pthread_mutex_init失败时的处理] (2)[hash表初始化是否完整]
```

### 销毁模板
```
[模块]资源销毁函数。销毁全局mutex、遍历hash表释放所有残留资源。请检查：(1)[pthread_mutex_destroy前是否确保无线程持有锁] (2)[hash表遍历释放是否遗漏资源] (3)[残留资源的释放顺序是否安全]
```

### 生成规则
- 初始化：关注初始化步骤的完整性和失败处理
- 销毁：关注遍历完整性、释放顺序、锁安全

## 7. 条件参数路径选择函数（高价值缺陷模式）

### 问题本质

释放函数本身被调用了，但传入的**条件参数不正确**，导致中心端走错了资源摘除分支。传统 paired_functions 规则认为"已配对"而漏报。

典型场景：客户端有两种角色(创建者/成员)，释放函数的条件参数决定中心端摘除哪类节点，但客户端硬编码了条件参数，导致某角色的摘除路径永远不会被触发。

### 识别特征

1. **释放函数有条件参数**：释放/关闭函数的参数列表中存在布尔型(`VOS_BOOL bIsXxx`)或枚举型(`XXX_TYPE eXxxType`)参数，该参数在函数体内被用于 if/else 分支选择不同的摘除路径
2. **调用方有角色标识字段**：调用方所在的结构体有角色/类型标识字段(如 `ucXdrtType`、`ucChanType`、`enSockMode`)，不同角色对应不同的资源类型
3. **条件参数被硬编码**：调用释放函数时，条件参数被硬编码为字面量(如 `VOS_FALSE`、`0`、`NULL`)而非根据角色字段动态计算

### 自动识别方法

分析函数源码时按以下步骤检测：

**步骤1**：识别释放函数调用中的字面量参数
```
搜索模式: xmeshXxxCloseRequest(..., VOS_TRUE/VOS_FALSE/0/1, ...)
或:       XxXxxFree(..., VOS_TRUE/VOS_FALSE, ...)
```

**步骤2**：读取释放函数的实现，检查该参数是否影响执行路径
```
搜索释放函数体中: if (stMsg.ucIsXxx == VOS_TRUE) / switch(eType)
如果该参数参与了条件分支 → 标记为"条件参数"
```

**步骤3**：在调用方结构体中查找角色标识字段
```
搜索模式: ucXxxType, enXxxMode, ucChanType, ucRole
这些字段通常在同一结构体中，且在创建/加入时被赋不同值
```

**步骤4**：判断映射关系是否正确
```
如果条件参数被硬编码 → 标记为"硬编码风险"
如果存在角色字段但未用于条件参数 → 标记为"映射缺失"
```

### 模板

**调用方（客户端，泄漏发生点）**：
```
[函数职责概述]。此函数在关闭[通道/连接]时调用[释放函数]向[中心端/服务端]发送关闭请求，[释放函数]根据[条件参数]决定摘除哪类节点：[条件参数=值A]时摘除[资源类型A]([摘除函数A])，[条件参数=值B]时摘除[资源类型B]([摘除函数B])。本函数可能释放的[通道/连接]有两种角色：[角色1]([标识字段]==[值1])和[角色2]([标识字段]==[值2])，必须根据角色传递正确的[条件参数]值。请重点关注：(1)[释放函数]的[条件参数]是否根据[标识字段]区分了[角色1]和[角色2] (2)如果硬编码为[硬编码值]，[某角色]关闭时[中心端]会走[错误摘除函数]而非[正确摘除函数]，导致[某资源类型]节点永远不被摘除而泄漏 (3)[创建/加入函数]时[标识字段]被设为[值1/值2]，请验证所有关闭路径都正确映射了角色到[条件参数]
```

**处理方（中心端，条件分支处理）**：
```
处理[消息类型]。中心端根据[条件字段]选择不同的资源摘除路径：[条件字段=值A]时调用[摘除函数A]摘除[资源类型A]，[条件字段=值B]时调用[摘除函数B]摘除[资源类型B]。这是两种不同资源的条件摘除，路径选择完全依赖客户端传递的[条件参数]。请重点关注：(1)两条摘除路径是否都正确执行了DDM_ListRemove+DDM_FREE (2)如果客户端传错[条件参数]值(如[某角色]关闭时传[错误值])，会导致[某资源类型]节点不被摘除而泄漏——请反向验证：调用[释放函数]的所有客户端代码是否都根据角色正确传递了[条件参数] (3)[某条件]下是否正确通知了[关联方]
```

### 生成规则

- **条件参数语义声明**：必须显式说明条件参数的分支含义（"bIsMember=TRUE时摘除成员节点，FALSE时摘除MCM组节点"），这是 LLM 自身难以从代码推断的领域知识
- **角色到参数的映射**：必须列出角色标识字段与条件参数的对应关系
- **硬编码风险警告**：当检测到 `VOS_FALSE`/`VOS_TRUE`/`0`/`1` 等字面量作为条件参数时，必须生成"如果硬编码为X，某角色关闭时会走错路径"的检查项
- **反向验证引导**：对中心端处理函数，引导 LLM 反向检查所有调用方是否正确传参
- 此模式可叠加在"资源释放函数"模板之上，作为额外的深度检查维度

### 完整案例：xmeshMcmSocketFree

**源码特征**：
- 调用 `xmeshMcmCloseRequest(pstInfo->pXdlink, VOS_FALSE, pstMcmFdInfo->llKey)` — `bIsMember` 硬编码为 `VOS_FALSE`
- 结构体有 `ucXdrtType` 字段，在创建组时赋 `XDRT_CHAN_WRITER`，加入组时赋 `XDRT_CHAN_READER`
- 释放函数 `xmeshMcmCloseRequest` 内部将 `bIsMember` 赋给 `pstReqMsg->ucIsMcmber`
- 中心端根据 `ucIsMcmber` 走 `CleanMemberInfoByKey` 或 `CleanMcmInfoByKey`

**生成的 custom_prompt**：
```
释放xmesh组播socket资源。此函数在关闭MCM通道时调用xmeshMcmCloseRequest向中心端发送关闭请求，中心端根据bIsMember参数决定摘除哪类节点：bIsMember=TRUE时摘除成员节点(CleanMemberInfoByKey)，bIsMember=FALSE时摘除MCM组节点(CleanMcmInfoByKey)。本函数可能释放的MCM通道有两种角色：创建者(WRITER，ucXdrtType==XDRT_CHAN_WRITER)和成员(READER，ucXdrtType==XDRT_CHAN_READER)，必须根据角色传递正确的bIsMember值。请重点关注：(1)xmeshMcmCloseRequest的bIsMember参数是否根据ucXdrtType区分了WRITER和READER角色 (2)如果硬编码为VOS_FALSE，READER角色关闭时中心端会走CleanMcmInfoByKey而非CleanMemberInfoByKey，导致成员节点永远不被摘除而泄漏 (3)创建组播组(xmeshMcmSetMcastAddr)时ucXdrtType被设为XDRT_CHAN_WRITER，加入组播组时ucXdrtType被设为XDRT_CHAN_READER，请验证所有关闭路径都正确映射了角色到bIsMember
```

### 完整案例：xmeshServerMcmCloseProc（中心端反向验证）

**源码特征**：
- 接收 `ucIsMcmber` 字段，走 `if (stMsg.ucIsMcmber == VOS_TRUE)` 分支
- TRUE → `xmeshServerCleanMemberInfoByKey` 摘除成员节点
- FALSE → `xmeshServerCleanMcmInfoByKey` 摘除MCM组节点
- 分支选择完全依赖客户端传值

**生成的 custom_prompt**：
```
处理XMESH_C2S_MSG_MCM_CLOSE_REQUEST。中心端根据ucIsMcmber字段选择不同的资源摘除路径：ucIsMcmber=TRUE时调用xmeshServerCleanMemberInfoByKey摘除成员节点，ucIsMcmber=FALSE时调用xmeshServerCleanMcmInfoByKey摘除MCM组节点。这是两种不同资源的条件摘除，路径选择完全依赖客户端传递的bIsMember参数。请重点关注：(1)两条摘除路径是否都正确执行了DDM_ListRemove+DDM_FREE (2)如果客户端传错bIsMember值(如READER关闭时传FALSE)，会导致成员节点不被摘除而泄漏——请反向验证：调用xmeshMcmCloseRequest的所有客户端代码是否都根据角色正确传递了bIsMember (3)MCM组关闭时(ucIsMcmber=FALSE)是否正确通知了所有成员退出(xmeshServerNotifyMemberMcmQuit)
```
