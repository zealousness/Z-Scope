# 01 · 范围、优先级与能力分期

## 产品目标

把 Z-Scope 做成能理解项目资源协议、主动发现复杂缺陷、用可核查证据控制误报并在夜间持续工作的专业扫描工具。通用编辑、修工程和写测试是后续扩展，不能成为专业扫描改进的前置框架。

五项目标按顺序约束取舍：先减少错误确认和错误排除，再扩大真实缺陷召回，然后优化相同质量与覆盖下的成本，持续沉淀项目模型并降低用户操作负担。低误报不能通过隐藏未决项实现；夜间时间较充裕也不意味着允许无界重复调查。

## 支持范围

| 范围 | 本次规划 |
|---|---|
| Linux 用户态 C/C++ | 第一阶段真实闭环；使用实际编译配置、目标 ABI、标准库和项目接口 |
| 嵌入式/RTOS | 第二阶段独立平台模型，覆盖任务/中断、静态内存池、DMA、设备句柄等；主机替身实验须标明限制 |
| C++ | 复用现有解析；显式建模 RAII、析构/异常退出、move、智能指针及自定义 deleter；不能将 C 的 malloc/free 规则直接当完整 C++ 语义 |
| Java | 保留当前产品路线；本次内存/资源主线不承诺新增 Java 专项能力，接口变更同步语言分发 |
| 无锁/弱内存、内核 | 按真实需求与后端适配独立推进；未支持时明确覆盖缺口 |
| 通用 Coding | 后置；按明确修复目标应用补丁、验证与交付，不默认修改扫描对象 |
| 网页访问 | 不建设。项目理解来自本地源码、构建、测试、文档和用户输入 |

## 人机分工

启动时一次确认：工程根与构建目标、平台、重点模块/资源、现有测试命令、可用时窗/资源，以及确实无法从资料推导的关键业务前提。已有正确配置直接“一键开始”，不每次重问。

运行中自主完成调查、建模、复现与失败恢复。业务语义不足则把相关义务标为条件性/未决，继续其余任务；等待模型或某后端失败不阻塞全部扫描。用户主动介入、停止、改变目标仍立即生效。

验收时按根因展示已确认问题，单列条件与未决缺口，用户批量确认业务模型、接受/否定报告和选择后续修复。反馈写回正确的知识域，而不是把否定一条告警变成全局静默。

## 不建设的前置设施

不新增权限审批/安全平台、代码冻结流程、多 Agent 团队、向量数据库、微服务集群、外部 Coding SDK 或网页工具作为首版依赖。确有重复职责可直接删除；数据身份、真实执行和结果可追踪是质量要求，不扩展成审批手续。

既有正式发行与 benchmark 有各自协议，本轮不执行也不宣称通过。普通开发不依赖这些正式流程；规划中的简化不得篡改历史成绩。
