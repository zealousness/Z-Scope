# 20 · 易配置、夜间运行与集中验收

## 设计目标

用户完成一次项目接入后，日常只需选择工程/范围并开始扫描，次日查看可理解的结果。前台不要求理解候选账本、证据轮次、RuntimeSpec、SCC、TTL 或 backend 内部参数。

本地 WebUI 与 CLI 共用同一服务和配置；不新增网页访问能力。通用聊天框不是首期使用入口，核心是准备、运行、验收三个清楚的页面/步骤。

## 1. 启动准备

展示一张项目卡：

- 工程位置与本轮实际源码版本（含未提交修改）。
- 检测到的语言、平台、构建目标/编译配置与测试入口。
- 扫描重点：默认内存、资源和异步生命周期，其余适用检查仍可选。
- 已理解的主要资源模型、文档冲突和关键未知。
- 模型/工具是否就绪，可选能力缺失的具体影响。
- 夜间时窗、机器/模型并发建议、自动复现开启状态与独立输出位置。

自动可确定的字段直接填入，用户只确认重要选择和冲突。多个链接目标不能静默选第一个；缺编译数据库时给可执行的构建导出建议，或明确局部源码分析的范围。

少量关键业务问题优先在此询问：队列失败后谁释放、注销是否等待在途回调、pool 生命周期、是否为 ISR/DMA 平台。未知允许保留；不能为获得“完整画像”强迫用户填完全部 API 表。

默认按钮为“开始夜间扫描”，可选“快速检查”和高级设置。已有配置无变化时不重复问题。配置误填指出字段/实际解析路径与修正方法，不直接展示 Python traceback。

## 2. 夜间运行

主视图显示：正在做什么、已完成范围、当前确认/待验证数量、后端状态、最近活动、资源/时间、停止与续跑。百分比必须有真实分母；动态发现阶段可显示阶段与工作项计数，不能伪造线性完成率。

不显示不断弹出的技术审批。业务问题记队列，保持具体影响与当前保守处理；其他任务继续。某后端不可用时显示哪些能力变为 partial，不把整页变成无法理解的失败日志。

WebUI 关闭后本地作业 owner 继续，重连读取持久状态。开始之前说明需要主机/WSL 与模型服务保持运行；机器休眠/退出后能恢复不等于离线期间仍执行。

时窗到达停止新工作并完成有限收尾，生成可验收的部分报告；支持继续剩余项。用户停止立即取消新调度，明确在途进程的结束状态。首期不承诺精确耗时预测或复杂周期调度。

## 3. 次日集中验收

首屏按根因列出已确认问题，展示类别、严重度、对象/资源、触发路径与关键位置；“条件性”“待验证”“覆盖缺口”明显可见，不藏在下载附件。

单条问题详情：

1. 一句话解释何时发生什么错误。
2. 申请/借用/转移/释放/访问的源码时间线；并发时按线程/任务分列。
3. 已成立的关键事实、尚待用户确认的前提、适用构建与平台。
4. 可查看/复跑的静态见证或复现材料，实际测试状态与限制。
5. 根因合并来源、相关位置、建议修复方向与验证建议。

高级页提供原始日志、完整证据和成本，不要求普通用户理解底层 schema。

反馈动作保持少而清晰：确认问题、这条是误报、补充业务前提、标记重复、暂时接受风险、创建后续修复任务。批量回答共同业务问题后，仅重算受影响对象/候选，不自动全仓重扫。

误报原因进入 Review Memory 或检测器改进；业务前提进入模型；风险接受是显式处置；重复进入去重。不会因为一次“误报”自动抑制所有相似函数。

## 4. 配置与模型编辑

一个 zscope.yaml，UI 表单与 CLI 参数同源。普通视图只包含工程、模型、目标、重点与运行偏好；工具路径、并发细节、特定验证器参数放高级区。

业务模型以“接口—何时成功—资源交给谁—何时回收—是否等待”的表单呈现，附源码/文档来源和冲突。工作簿可导入/导出，但不作为唯一必需交互方式。

没有兼容要求，允许新版本简化或重命名旧字段。发布说明提供一次性改写示例，保留人工模型/反馈导出；不把旧缓存迁移复杂度转嫁给普通用户。

## 5. 可用性验收

- 首次启动能从真实工程自动形成可用配置，不靠开发者手改多处内部文件。
- 日常扫描只需少量操作；记录实际耗时和用户补填次数后设改进目标。
- 夜间没有因普通业务未知而等待人答复，次日问题合并且有影响说明。
- 任一确认结果能定位源码与条件，任一 partial 能说明剩余工作。
- 键盘操作、清晰状态文字、合理对比度与空/错/加载状态完整，不能只用颜色区分结果。
- CLI 与 Web 的范围、配置和结果一致，取消/续跑真实生效。
- 不把原始 API key、巨大 JSON 或内部堆栈作为普通页面内容。
- 网页搜索/抓取不出现在入口、工具和帮助中；本地 WebUI 正常运行。

U01 从首条切片开始，U02 随四态结果与夜间作业落地；不再把易用性留到全部后端做完之后。
