结论：**不建议现在直接删除工具代码**。更合理的是：

1. 保留核心工具。
2. 把低 ROI 工具从默认可见集合里降权/按需启用。
3. 合并部分“图/数据流/间接调用”类工具的使用入口。
4. 新增更高层的 evidence pack 工具，减少 Agent 自己拼上下文。

**建议保留的核心工具**

| 工具 | 判断 | 理由 |
|---|---|---|
| `get_function_snapshot` | 必留 | 成功率 100%，是低成本语义上下文核心 |
| `get_file_snippet` | 必留但要优化 | 最高频工具，证据价值高，但重复调用严重 |
| `get_function_impl` | 必留 | validator 取完整实现时需要，错误率低 |
| `get_type_info` | 必留但要优化 | 类型信息对 C 漏洞判断关键，但 Type not found 偏高 |
| `get_callers` | 必留 | 调用者查询轻量，证据命中率高 |
| `get_call_graph` | 必留 | validator 使用较多，路径验证需要 |

**建议保留但默认降权/按需启用的工具**

| 工具 | 判断 | 原因 |
|---|---|---|
| `list_known_functions` | 不删，但不要默认给 validator 大量使用 | 当前 561 次调用，证据命中率 0%，更像泛化搜索 |
| `get_data_flow` | 不删，但应强条件触发 | 当前空结果率 100%，说明默认使用方式收益很低 |
| `find_function_pointers` | 不删，但只在 callback/dispatch 场景启用 | 当前调用少且空结果 100%，但对函数指针漏洞仍可能关键 |
| `query_pointer_alias` | 保留，按 temporal/shared-state 场景启用 | 当前调用少但证据命中率 83.33%，有价值 |
| `verify_taint_reachability` | 保留但收紧参数 | 空结果率 57.58%，需要明确 source/sink 后再调用 |
| `get_deep_call_context` | 先别删 | 当前 0 调用是因为默认 workflow 下不可见，尚未被真实评估 |

**可以考虑合并的方向**

不建议把底层工具物理删除式合并，但可以增加更高层入口：

| 合并方向 | 建议 |
|---|---|
| `get_data_flow` + `verify_taint_reachability` | 合成一个更明确的 `trace_source_to_sink`，返回可达性、路径、guard、失败原因 |
| `find_function_pointers` + `query_pointer_alias` | 合成 `resolve_indirect_targets`，专门处理函数指针、callback、alias |
| `get_callers` + `get_call_graph` | 底层可共用实现，但 API 仍建议保留轻量版和完整图版 |
| `get_function_snapshot` + `get_file_snippet` + `get_type_info` | 不直接合并，新增高层 `get_evidence_pack` 来按需组合 |

**目前工具是否完全满足项目需求？**

不完全满足。现在工具偏“原子查询”，Agent 需要自己多轮拼证据，所以导致：

- snippet 调用过多；
- validator token 很高；
- 数据流/函数指针工具低 ROI；
- 类型/函数名错误需要 Agent 自己修正；
- 证据包缺少统一结构，后续证据命中率也只能粗略估计。

**值得新增的工具**

| 新工具 | 价值 |
|---|---|
| `get_evidence_pack` | 给 validator 一次性返回 issue 相关 snapshot、snippet、call path、types，减少重复调用 |
| `resolve_symbol` | 统一解析函数/类型/宏/字段名，降低 `Function not found` 和 `Type not found` |
| `trace_source_to_sink` | 替代零散 dataflow/taint 查询，直接服务漏洞可达性判断 |
| `resolve_indirect_targets` | 专门处理函数指针、callback、dispatch table |
| `get_candidate_context` | 根据 candidate_id 返回后端候选的最小证据上下文 |
| `get_file_outline` | 返回文件内函数/类型/全局变量概览，替代部分 `list_known_functions` 泛搜 |

我的建议是：**12 个现有工具都先保留代码，但默认 workflow 里只暴露高 ROI 工具；低 ROI 工具改成 skill/candidate 条件触发；新增 2-3 个复合证据工具来减少 Agent 自己反复拼上下文。**
