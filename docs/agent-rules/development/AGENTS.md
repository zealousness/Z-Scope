# 开发者路线

[返回根入口](../../../AGENTS.md) · 功能、修复、架构、Agent/Skill/Workflow、后端、报告和测试变更时读取。

适用于功能开发、缺陷修复、架构调整，以及 Agent、Skill、Workflow、后端、候选、验证、报告或测试变更。

1. 先读 `docs/architecture.md`，再按 [`docs/modules/README.md`](../../../docs/modules/README.md) 进入对应子系统。
2. 修改前搜索调用方、配置模型和现有测试；不要仅凭文件名推断所有权。
3. 保持用户已有修改，不重写无关文件，不提交密钥、私有 endpoint 或本地 benchmark 配置。
4. 制定计划（包括计划模式）与执行时，按实际改动、调用依赖和对应专题选择针对性测试；不默认对未受影响的既有功能全量回归，也不把重复已通过检查作为例行步骤：

   ```bash
   python -m pytest -q <相关测试>
   ```

   只有明确跨模块影响、真实故障证据或用户明确要求时，才扩大测试范围，并简要说明覆盖的实际影响。相关检查通过后，除非新改动或故障证据影响结论，不再重复。专题要求的 native 实测、正反例和相关回归仍按触发条件执行。

   `compileall` 和 `mypy` 按本次 Python 改动的实际影响选择范围；下面是需要全仓检查时的命令，不是每次任务默认执行的清单，纯文档改动不运行：

   ```bash
   python -m compileall -f -q zscope scripts test tests
   python -m mypy zscope
   ```

   测试与质量命令一律在 Linux 环境执行；Windows 上必须在 WSL Linux 用户态中运行（在 WSL 虚拟环境安装并执行），不要用原生 Windows 解释器形成测试结论。

5. 仅对需要格式化的 Python 变更运行 Black，避免无关的大范围格式化。

## 实施与验证的默认方式

- 在当前授权目标内直接实现可运行改动，计划随源码与验证结果更新。不先冻结提交号、文件哈希、修改清单或整仓副本；旧计划中的哈希变化本身不构成拒绝修改或重新审批的理由。确有并发编辑冲突时，只处理冲突文件并保留他人修改。
- 快照、独立工作区、归档和 dry-run 只在复现问题、隔离实际冲突、确认有副作用的命令或用户明确要求时使用，不默认串成“冻结 → 快照 → dry-run → 审批 → 实施”。实际命令已有准备/校验步骤时，不再手动重复一套相同流程。
- 测试先回答本次质量目标：缺陷是否复现并修复，反例是否仍正确，受影响的消费者是否可用。复用已有有效用例，只补当前行为缺口；不以轮数、用例总数或材料数量代替质量结论。目标未满足时定位缺口并修复，不靠重复跑不相关测试凑“通过”。
- 已通过结果只在依赖它的源码、配置、工具或输入变化后重新核对；按实际影响补跑。构建身份、缓存摘要与运行时收据仍由产品校验，失效时更新相关产物，不把一次失效推广成所有既有功能重新验收。
- 文档与历史记录中的测试列表是相关入口；只执行命中行为的用例或模块。确实改动共享调度、事实模型或跨模块合同才扩大覆盖；真实 native、模型或发行工具行为需要对应实际执行，dry-run/合成事件不能代替它们。

涉及构建身份、协议、规则开发或 Range 时，再按[根入口](../../../AGENTS.md)读取命中的专题；不预读全部专题。
