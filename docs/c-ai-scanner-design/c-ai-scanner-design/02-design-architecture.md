# 02 · 设计架构

[返回文档导航](README.md) · [能力地图](01-capability-map.md) · [预期目标](03-objectives-and-metrics.md) · [实施路线](04-delivery-roadmap.md)

## 1. 架构总览

```text
真实构建 / 链接目标 / 平台配置 / 运行接口
                    │
                    ▼
        编译语义前端 + 项目事实库
                    │
                    ▼
   对象模型 + 事件模型 + 条件化函数摘要
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   内存静态分析  并发静态分析  AI 主动探索
        └───────────┼───────────┘
                    ▼
                统一候选库
                    │
                    ▼
   语义补全 → 切片 / 按需精化 → 局部验证
                    │                 │
                    │        并发模型检查 / 动态复现
                    └─────────┬───────┘
                              ▼
                    见证检查 / 证据分级
                              │
                              ▼
                    根因去重 / 正式报告

贯穿各层：构建快照、契约来源、未知状态、依赖记录、预算与评测。
AI 语义建模向事实层提出契约；经校验或明确接受后才能成为分析依据。
```

**分析单位：一个对象在一组可达操作与执行上下文中是否可能进入错误状态。** 函数是分析与复用边界，不是缺陷发现的唯一粒度。

## 2. 模块职责与接口边界

| 模块 | 输入 | 输出 | 不应承担的职责 |
| --- | --- | --- | --- |
| 构建适配器 | 编译数据库、构建/链接信息、目标配置 | 明确程序范围的构建快照、编译实例、覆盖缺口 | 用随意补宏或伪造类型掩盖解析失败 |
| 编译语义前端 | 构建快照与源码 | 符号、类型、控制流、调用关系、源码映射 | 仅按名称合并不同模块的符号 |
| 事实与摘要层 | 编译事实、已接受契约 | 对象、事件、条件化摘要、依赖与未知状态 | 把 AI 自然语言推测直接变成安全事实 |
| 内存/并发引擎 | 对象事件、摘要、执行上下文 | 候选、路径假设与缺失证据 | 把粗抽象中的可能性直接当实际缺陷 |
| AI 协作层 | 有范围的代码、事实、契约与候选 | 语义提议、探索候选、下一步查询/验证任务 | 以模型置信度或多数投票裁决缺陷 |
| 验证协调器 | 候选及未满足的证明义务 | 精化任务、验证结果、见证或排除理由 | 将超时、未复现解释为安全 |
| 证据与报告层 | 验证结果、模型假设与源码映射 | 状态分级、根因报告、覆盖/未决说明 | 隐藏条件、混淆严重度与确认程度 |
| 增量与调度层 | 全部产物依赖、预算和历史结果 | 缓存命中、失效集合、任务优先级 | 仅按修改文件或调用图决定失效 |

各后端可以保留自己的内部表示；必须对齐同一构建、源码位置、目标语义和关键环境假设。不要求先建设一套包办所有后端的统一 IR。

## 3. 核心数据模型

### 3.1 构建与符号身份

构建快照至少包括源码版本、编译参数、宏、头文件依赖、目标 ABI、链接目标和契约版本。编译实例不能只以 `.c` 文件路径标识；同一源码以不同配置编译时应分别建模。

符号身份区分翻译单元、链接作用域、目标配置和实例化后的定义，避免把不同模块中的同名 `static` 函数或变量合并。

解析失败、缺头文件、未知扩展等必须成为结构化覆盖缺口。源码级探索仍可继续，但不得输出与完整编译语义分析同等级的结论。

### 3.2 对象与存储区域

| 维度 | 需要记录的信息 |
| --- | --- |
| 身份 | 分配点、调用上下文、对象来源、是否代表多个实际实例、生命周期代际 |
| 空间 | 基对象、子对象/字段、偏移、大小、访问区域、已初始化区域 |
| 生命周期 | 未分配、存活、已释放、已失效、未知 |
| 责任与共享 | 独占、借用、转移、共享、引用计数、逃逸目标 |
| 来源 | 源码事实、推导结果、已接受契约、待验证假设 |

初始阶段允许合并抽象对象以控制成本；当合并引发别名、UAF 或 double free 候选时，再区分上下文与实例。不得将抽象对象相同直接认定为实际对象相同。

### 3.3 语义事件

事件类型包括分配、释放、读取、写入、初始化、指针保存、所有权转移、对象发布、加解锁、条件等待、原子操作、线程创建/结束、回调注册/注销、任务提交/完成。

每个事件关联：对象与区域、所在函数/执行上下文、路径条件、同步信息、源码位置、事实来源和完整性状态。

异步提交不仅是一次函数调用，还可能意味着对象逃逸、所有权转移、未来访问和调用者责任变化。

### 3.4 条件化函数摘要与契约

摘要必须保留不同返回分支的关系，而不是只写“可能释放参数”。例如：

```yaml
function: queue_submit
cases:
  - when: "ret == SUCCESS"
    ownership: "p 转移给队列"
    effects: ["队列保留 p", "消费者以后可能访问 p"]
  - when: "ret != SUCCESS"
    ownership: "p 仍属于调用者"
    effects: ["队列不保留 p"]
provenance: "实现推导 / 维护者接受的契约 / 待验证假设之一"
```

摘要还应表达返回值/参数关系、别名与逃逸、初始化、共享访问、锁状态变化、未知副作用和依赖。

函数内部分析与调用点摘要组合分离；递归调用关系采用固定点计算。需要确认候选时，按需展开相关上下文，不做全仓无限内联。

未知外部函数不能默认纯函数或无副作用：发现阶段保留相关可能性，确认阶段补齐影响结论的关键语义。未知语义影响大量候选时，优先建模公共接口。

### 3.5 统一候选与证据记录

以下是逻辑字段示意，不是要求首版一次实现的完整接口规范：

```yaml
candidate_id: CAND-0001
kind: use_after_free
build_ref: target-a/debug
object_ref: object-42
sources: [memory_engine, ai_explorer]
locations: ["取得指针的位置", "销毁位置", "使用位置"]
claim: "存在取得指针、销毁对象、随后使用旧指针的合法执行顺序"
established_facts: ["取得与使用事件已定位"]
open_obligations:
  - "证明三个事件针对同一代对象"
  - "确认销毁接口语义"
  - "排除引用持有或等待机制对该顺序的阻止"
assumptions: []
evidence: []
status: pending
status_reason: "关键对象身份与执行顺序尚未确认"
dependencies: ["相关摘要", "对象访问集合", "契约与构建配置"]
```

严重度、确认状态和外部可利用性分别记录，不能把“潜在影响严重”误当“证据充分”。

## 4. 内存引擎

采用“组合式摘要提供覆盖，精确路径负责确认”的路线。

1. 全局提取相关分配、释放、访问、返回和逃逸事件，不仅围绕外部输入入口分析。
2. 根据生命周期、边界、初始化和所有权关系生成候选。
3. 收集候选的对象身份、路径可行性、调用前提和接口语义缺口。
4. 按需升级字段敏感、上下文敏感、路径敏感及目标整数语义分析。
5. 对候选交付错误见证，或保留/排除相应路径。

重点边界：

- 越界验证保留整数宽度、符号转换、乘法溢出和子对象边界，不能只用数学整数公式。
- 空指针缺陷需存在满足契约的实际调用或输入，不能仅因函数没有判空而报告。
- UAF 与 double free 需要区分对象实例及生命周期代际。
- 泄漏以责任边界为准，不能仅因当前函数未释放就报告。

“不对所有输入都必错”不构成排除理由。存在一个符合程序环境与接口契约的可达错误执行即可支持缺陷；人为违反契约制造的调用则不应冒充真实触发路径。

## 5. 并发引擎

### 5.1 普通数据竞争

围绕对象存储区域建立访问关系，结合可能并行执行关系（MHP）和 happens-before（HB）判断。需要同时考虑实际别名、至少一个写、两个访问在同一次执行中可共同到达，以及是否有充分同步关系。

锁集合用于快速筛选，不是完整裁决。同步模型需要真实锁实例、读写模式、成功条件、线程创建/等待、任务串行化及原子读取关系。

仅在代码中同时出现 acquire/release，不能证明某两次访问已经同步；必须关联具体原子对象和相关读取关系。未建模同步原语应触发语义补全，而不是直接认定“没有同步”。

### 5.2 并发生命周期

内存与并发引擎共享对象及代际。需要识别下面这种全部在同一把锁下仍然错误的调度：

```text
A：加锁 → p = g → 解锁
B：加锁 → free(g) → g = NULL → 解锁
A：加锁 → 使用 p->value → 解锁
```

锁使各步串行，却未保证 `p` 后续仍有效。分析不能因共同持锁就剪掉这个生命周期候选。

重点覆盖借用后销毁、异步提交后提前释放、取消/超时与正常完成重复回收、回调注销后仍在执行，以及引用取得之前的失效窗口。

### 5.3 协议与弱内存

死锁不能仅由锁顺序图存在环来确认；需验证持锁、等待与路径可以共同发生。

原子性、发布与回收错误需绑定明确不变量或状态机。复杂无锁与弱内存问题交给匹配目标模型的专用后端；用户态 C、内核与 RTOS 语义不得混用。

## 6. AI 工作方式

AI 承担四类任务：项目契约发现、对象/协议级主动探索、证据缺口规划、复现驱动与报告生成。

提供给 AI 的工具应以有类型的查询为主，例如：查询对象事件、追踪别名、读取条件化摘要、解析回调目标、获取生命周期切片、验证路径、执行定向测试。返回结果包含来源位置和完整性状态。

关键控制：

- AI 生成的语义先是提议，不自动成为安全保证。
- 主动探索独立于传统扫描器告警，避免发现范围被已有规则锁死。
- AI 可以选择下一步查什么，但不能把“没查到”理解为“不存在”。
- 关键约束由编译语义或受校验契约生成；LLM 任意编写的 SMT 得到 SAT 不构成漏洞证书。
- 多个模型结论一致只可调整优先级，不增加独立证据等级。

## 7. 验证与结果状态

### 7.1 按缺陷类型满足证明义务

验证不是再让另一个 Agent 阅读一遍，而是落实候选所需的前提。例如 UAF 至少检查同一代对象、确切失效语义、合法执行顺序，以及不存在阻止该顺序的必要持有/等待约束。

候选切片需包含数据、控制、别名、相关调用和并发干扰。另一线程中的销毁路径即使不在当前调用栈，也可能是不可删除的上下文。

### 7.2 后端结果解释

| 结果 | 允许得出的结论 |
| --- | --- |
| 过度近似模型中出现反例 | 仍是候选，继续精化或具体化 |
| 忠实模型中有可映射回原程序的错误见证 | 支持正式缺陷；须保留构建、契约和环境范围 |
| 某条路径约束不可满足 | 排除该路径，不自动排除其他路径 |
| 有界验证未发现错误 | 仅在检查范围内未发现，不能泛化为程序安全 |
| 未复现、超时、模型不完整 | 保留未知与具体原因 |

有界验证也可以给出有效错误见证；需要检查反例不是由不合法截断、错误桩函数或不忠实抽象制造的。证明未发现错误与发现一个真实反例，证据要求不同。

### 7.3 动态验证

按缺陷类型使用独立的运行时验证配置，如 ASan 与 TSan，不要求所有验证器在同一个二进制内同时启用。

复现驱动须符合接口契约与初始化要求；关键被测实现保持真实；桩函数不得凭空增加释放、删除同步或改变责任转移。调度控制也要检查是否引入新的同步关系、改变目标错误。

动态结果需要结合插桩覆盖、运行环境和驱动有效性检查。静态缺陷未动态复现，不自动撤销已有有效静态见证；动态告警也不自动越过证据审查。

### 7.4 四类状态

| 状态 | 含义 | 报告方式 |
| --- | --- | --- |
| 已确认缺陷 `confirmed` | 关键证据成立，见证在声明范围内有效 | 正式报告；是否阻断 CI 另行配置 |
| 条件性缺陷 `conditional` | 错误机制成立，但实际环境前提尚未确认 | 单列条件，不计入主要正式召回 |
| 待验证 `pending` | 别名、路径、契约、模型或预算不足 | 保留候选和下一步动作 |
| 已排除候选 `ruled_out` | 候选所声称的错误在声明范围内已被排除 | 保存原因；若仅排除部分路径，候选仍保持待验证 |

结论随代码、构建或契约变化可以失效并重新打开。不能因为验证过程尝试过若干失败路径，就关闭尚有其他可能路径的候选。

## 8. 报告、复用与调度

### 8.1 正式报告最小内容

每条报告包括缺陷类别与根因、关键源码位置、对象及生命周期、输入或线程执行顺序、适用构建与契约、证据来源、剩余限制，以及可复用的见证或复现材料。

根因去重合并重复来源和相同因果链，但保留不同对象、触发条件或独立根因，避免用过度合并美化误报指标。

### 8.2 性能设计

一次解析与摘要尽量复用；先做廉价全局覆盖，再对必要候选支付高精度分析成本。并发事件先按对象、区域和上下文分组，不全仓两两配对。

调度优先解决高影响语义缺口：一个自定义接口模型若可影响数百个候选，应优先于逐条重复 LLM 审查。同时保留主动探索预算，避免复杂新问题长期饥饿。

预算不足只降低本轮完成度，不降低证据标准，也不把未完成候选标为安全。

### 8.3 增量失效

复用依赖不仅包括调用关系，还包括对象别名、共享访问集合、回调注册、构建配置、接口契约，以及“没有其他访问者”这类否定性结论。

例：旧版本某对象仅由一个线程访问；新版本增加另一线程访问。旧函数即使完全未改，依赖单线程访问假设的结果也必须重新分析。

增量正确性需以相同配置下的全量结果为对照，检查既有依赖变化和新增依赖。不能将“只重扫修改函数及调用者”宣传为完整影响分析。

## 9. 技术候选与集成策略

| 层次 | 原方案技术候选 | 本设计中的拟用角色 |
| --- | --- | --- |
| 编译语义 | Clang | 真实构建解析、类型/控制流、源位置与符号映射 |
| 顺序内存候选 | Infer / Pulse | 原型复用；参考条件化、可组合摘要与潜在问题传播 |
| C 并发候选 | Goblint | 作为候选发现通道之一，接入统一证据流程 |
| 局部路径验证 | CBMC | 验证局部 C 路径、对象与整数语义 |
| 并发模型验证 | GenMC | 验证匹配内存模型的局部并发与弱内存候选 |
| 运行时检查 | ASan / TSan | 提供经环境和驱动校验的动态证据 |
| AI 层 | 可替换 LLM 与工具调用运行时 | 语义发现、主动探索、验证任务规划与解释 |

以上为选型候选，不是已完成集成的结论。PoC 应核查目标语言扩展、构建与平台兼容性、许可、源码映射、数据交换及实际成本；不要求首版同时集成所有后端。

重点自研的是对象身份、项目契约、候选与证明义务、见证映射和增量依赖，而不是重复实现每一种求解器。
