 # 对于正负号写反这种逻辑漏洞，应该如何发现？

Listed directory bounds_and_integer
Viewed SKILL.md:1-35

对于**正负号写反、比较方向相反、增加/减少方向写反**这类逻辑漏洞，传统的静态分析工具（SAST）极难发现，因为无论是 `+` 还是 `-`、`>` 还是 `<`，在 C 语言语法上都是完全合法的，编译器和单纯的 AST 匹配器不会报错。

在 Z-SCOPE 中，发现这类“隐蔽逻辑漏洞”主要依赖**以下三条技术支路**的协同配合：

---

### 1. 语义契约与实现的“双层对比”（Semantic Mismatch Detection）
这是 Z-SCOPE 引入大模型 Agent 面板的核心价值所在。

* **步骤 1：提取设计意图（Intent）**
  在 Step 2 语义建模阶段，[semantic_modeler](file://wsl.localhost/Ubuntu-22.04/home/jager/Z-Scope/zscope/agents/semantic_modeler) 会阅读函数声明、实现和函数上方的注释块。
  * 例如，注释中写着：`/* Decrement reference count and free if zero */`（减少引用计数，若为0则释放）。
  * 语义建模 Agent 提取出该函数的意图契约：**副作用是减少引用计数**。
* **步骤 2：代码逻辑对齐审查**
  在漏洞挖掘阶段，[vulnerability_analyzer](file://wsl.localhost/Ubuntu-22.04/home/jager/Z-Scope/zscope/agents/vulnerability_analyzer) 会对照快照契约去审查实际代码。如果代码中写成了 `object->ref_count++`（正负号/增减写反），或者在释放分支上写了 `if (ref_count > 0)` 导致逻辑相反，Agent 会立刻捕捉到**“注释/契约承诺”与“实际算术代码”之间的语义冲突 (Semantic Mismatch)**，从而报出逻辑漏洞。

---

### 2. 状态机与控制流图规则（State Machine & CFG Matcher）
对于通用的并发和资源管理，Z-SCOPE 的 [GraphCandidateGenerator](file://wsl.localhost/Ubuntu-22.04/home/jager/Z-Scope/zscope/core/candidates/graph.py) 内部维护了算术状态机的期望走向。

* **引用计数竞态与生命周期**：
  在 C 语言中，释放资源通常伴随引用计数的**减少**。如果数据流追踪显示，某路径在执行 `free` 之前对引用计数执行了 `++` 操作，或者对非原子变量进行了修改，图规则判定器会将其标记为 `refcount_race` 或 `use_after_free` 候选。
* **锁配对与回滚反转**：
  在函数的错误处理（Error Cleanup）路径中，所有的状态恢复和锁释放操作，其逻辑方向必须与函数入口处的申请操作相反。如果申请时加锁，错误路径也写成了加锁（或者解锁写反），控制流图（CFG）的锁状态机轨迹会出现不闭合，从而被确定性规则捕获。

---

### 3. 数据流下溢/溢出守卫校验（Underflow & Overflow Guard check）
当正负号或大小比较写反时，往往会直接导致**整数下溢（Underflow）**或**边界检查失效**。

* **数值下溢候选**：
  在算术规则 [SKILL.md](file://wsl.localhost/Ubuntu-22.04/home/jager/Z-Scope/zscope/skills/bounds_and_integer/SKILL.md) 中，Z-SCOPE 强制追踪所有执行 `-` 或 `--` 的变量。如果在减法执行前，代码中没有前置的下溢保护（如 `if (count <= 0)` 或 `if (a < b)`），或者比较方向写反了（如写成 `if (count >= 0) count--;`，当 count 为 0 时仍会减到 -1），这会直接触发 **`bounds_and_integer`** 的下溢 Candidate，被 Deep Worker 送去人工/Agent 二次验证。
* **后置防溢出检查漏洞**：
  开发者常写出 `if (offset + len < offset)` 来防止溢出。但在现代有符号 C 编译期优化中，有符号溢出是未定义行为，编译器会直接把这个 check 优化掉。Z-Scope 的静态规则检测到这种“后置溢出校验”时，会直接将其视作无效防范（算反了阶段），强制要求改为前置校验（如 `if (len > LIMIT - offset)`）。

### 💡 本次运行中的真实案例

在你的本次测试中，就有两个非常典型的例子：

* **案例 A（增减/谓词判定写反）**：
  * **漏洞位置**：`RANGE-027`（`_lifecycle_wait_for_work`）
  * **表现**：代码在共享谓词判断 `g_lifecycle.pending_jobs == 0` 为真时，竟然执行了 `g_lifecycle.pending_jobs--`，导致整数直接下溢。Z-SCOPE 成功通过控制流谓词冲突与下溢漏洞规则将其合并检出。
* **案例 B（位偏移计算写反）**：
  * **漏洞位置**：`ISSUE_2`（`_runtime_find_bitmap_delta`）
  * **表现**：线位图字节序没有规范化，大端和小端下使用 `__builtin_ctzll` 计算出的偏移量刚好是相反的（一个小端算 1，大端算 7）。Z-SCOPE 的 `byte_order_logic` 规则识别到 memcpy 后的字级操作在缺少架构适配时计算方向反转，报出了该漏洞。
