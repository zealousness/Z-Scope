# 04 · 分阶段实施与交接路线

[返回文档导航](README.md) · [能力地图](01-capability-map.md) · [设计架构](02-design-architecture.md) · [预期目标](03-objectives-and-metrics.md)

## 1. 实施原则

先建立一条能运行、能解释、能验证的缺陷闭环，再扩展缺陷与项目语义，最后在质量基线下优化规模和性能。

不先建设复杂多 Agent 编排，不要求首版接入所有分析后端，也不以“解析了多少行代码”代替“正确交付了多少缺陷”。公共基础与第一个可验证缺陷应并行推进，避免长期只有框架没有结果。

下列阶段按依赖排序，不含未经项目资源评估的工期承诺。

## 2. P0：程序范围、事实模型与评测底座

**目标：确保分析的是正确程序，并有可判断对错的测试材料。**

| 工作包 | 主要能力 | 交付物 |
| --- | --- | --- |
| 确定首个支持环境 | F01、F07 | 一个明确的构建目标、平台与配置；支持/不支持的扩展、资源和同步原语说明 |
| 构建与语义导入 | F01–F04 | 编译实例、链接范围、符号身份、源码定位、基本对象与事件 |
| 覆盖与失败记录 | F07、E02 | 解析失败、未知调用和未建模语义的结构化记录 |
| 首批评价集 | E06 | 基础真缺陷、安全反例、修复前后样例及统计脚本 |

验收重点：同源不同配置、同名静态符号不会混淆；解析失败不会消失；每个基础事件能定位原始代码；测试集有明确预期，而不是仅看工具是否运行完成。

首轮环境可以收敛为一个用户态 C 目标和一组常用分配/线程接口，但这是降低 PoC 范围的实施选择，不代表完整产品只支持这一环境。

## 3. P1：最小可信缺陷闭环

**目标：交付首批证据充分的内存问题与基础并发问题。**

| 工作包 | 主要能力 | 交付物 |
| --- | --- | --- |
| 摘要与基础契约 | F05、F06 | 标准分配释放、常用同步接口、返回分支与所有权摘要 |
| 基础缺陷发现 | M01–M04、C01–C04 | 越界、空指针、UAF、double free、基础数据竞争及生命周期候选 |
| 统一证据流程 | V01–V03、V06、E01 | 候选结构、证明义务、路径验证、四类状态及根因报告 |
| AI 验证协作 | A03、A04 | 受控事实查询、针对证据缺口的下一步动作、合法复现材料 |
| 可选动态通道 | V05 | 至少一条适配首批缺陷的可信运行时复现通道 |
| 基线评价 | E02、E06 | 正式精确率、候选/最终召回、未决原因、覆盖与成本 |

### 建议优先贯通的纵向样例

采用一个包含跨函数创建、保存、销毁、使用的对象；并发版本加入真实共享对象和锁。让系统完整完成：

```text
导入真实构建
→ 识别同一代对象及相关事件
→ 生成 UAF 候选
→ 列出并补齐销毁语义与执行顺序
→ 得到可映射回原程序的见证
→ 输出含前提和源码位置的正式报告
```

随后加入不会 UAF 的对应反例：不同对象实例、使用前重新获取有效对象、引用持有或等待机制阻止销毁。只有反例也能正确处理，才说明工具不是仅识别表面代码形状。

P1 不要求所有类别都达到产品级覆盖。其完成标志是端到端机制真实有效、状态可信、指标可测，而不是展示一个无法复现的高精确率数字。

## 4. P2：语义与召回扩展

**目标：解决成批未决候选背后的语义缺口，并发现基础规则之外的问题。**

| 工作包 | 主要能力 | 交付物 |
| --- | --- | --- |
| 自定义资源 | F06、M06–M08、A01 | 内存池、引用计数、包装分配器及条件化责任转移模型 |
| 异步生命周期 | C04、C05 | 任务提交、完成、超时、取消、关闭、回调注销等协议分析 |
| AI 主动探索 | A02、A03 | 对象/协议级探索任务，不依赖已有扫描器告警才能启动 |
| 扩展验证 | V02–V05、C06–C08 | 并发切片、死锁/原子性验证，按需接入弱内存后端 |
| 净收益评价 | E06、E07 | 分类型质量变化、AI 消融、人工成本和未决原因变化 |

实施优先级由基线暴露的问题决定。一个接口阻塞大量候选时，优先建立可追溯模型；不是先增加 Agent 数量或无差别扩大上下文。

验收重点：新增语义能带来可观察的候选确认或误报减少；AI 主动探索发现的缺陷仍遵循同一证据标准；取消、注销、引用计数等安全反例不被批量误报。

弱内存、内核或 RTOS 支持需独立声明边界，不能仅复用用户态互斥锁模型后声称支持。

## 5. P3：质量约束下的规模化

**目标：在相同覆盖与质量水平下，降低大仓全量和增量成本。**

| 工作包 | 主要能力 | 交付物 |
| --- | --- | --- |
| 结构化复用 | E03 | 事实、摘要、契约、见证及依赖的持久化复用 |
| 精确失效 | E04 | 代码/构建/契约/共享事件变化和新增依赖触发的重新分析 |
| 对象级并发裁剪 | E05、C01–C04 | 分组配对与安全剪枝，区分数据竞争和生命周期性质 |
| 验证与 AI 调度 | E05 | 公共语义缺口优先、按需精化、主动探索预算与未决记录 |
| 大仓评测 | E06 | 冷启动、重复全量、增量的质量/覆盖/成本对照 |

增量回归至少包括：增加新线程访问者、新增回调目标、修改公共契约、修改头文件/宏、改变链接目标，以及删除原先提供同步或持有保证的行为。

验收重点：与全量对照没有未解释的结论或覆盖损失；预算用尽不会转换成安全；加速不是由减少构建、跳过难例或省略验证造成的。

## 6. 每个工作包的最小交接材料

工程任务保持以下五项即可，不先引入复杂流程：

1. **目标与范围：** 对应能力编号、本次要处理的缺陷/平台/接口，以及明确不覆盖的内容。
2. **输入输出：** 使用哪些现有事实，新增哪些结构化产物，接口如何被后续模块消费。
3. **真缺陷与安全反例：** 至少有正反两类样例；修复前后对照适用时一并提供。
4. **运行与证据：** 可执行命令、构建配置、见证/复现材料、已知限制和状态说明。
5. **评价变化：** 精确率、召回、覆盖、未决与成本的实际变化；没有数据时明确未测。

测试数量与规模随工作包确定，不把形式化材料数量当作研发成果。

## 7. 需要在实施中明确的决策

| 决策 | 何时解决 | 决策依据 |
| --- | --- | --- |
| 首个受支持平台与构建目标 | P0 | 可获得真实构建和缺陷材料，便于建立闭环 |
| 首批缺陷类别 | P0–P1 | 证据规则清楚、价值高、能够构建安全反例 |
| 后端复用还是自研 | P1 原型后 | 精度、兼容性、数据可访问性、许可与集成成本 |
| AI 运行位置与模型 | 启用相关任务前 | 代码保密要求、工具能力、准确率、成本与可复测性 |
| 正式报告阈值与 CI 策略 | 有足够基线后 | 分类型实测和人工复核，不用模型置信度替代 |
| 更复杂内存模型与平台扩展 | P2 | 实际项目需求与验证后端适配能力 |
| 召回与性能绝对目标 | 基线建立后 | 已知缺陷规模、项目复杂度、资源预算与质量约束 |

## 8. 第一轮交付应当回答的问题

**能否从一个真实 C 构建中，正确识别对象生命周期，发现一条真实内存或并发错误，在对应安全反例上不误报，并给出原程序中可核查的执行见证？**

这个闭环成立后，再扩大覆盖、增强 AI 主动探索和优化增量，才有可信的技术基础。
