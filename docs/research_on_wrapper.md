核心做法不是让 LLM 记住一张 `xxx_alloc ↔ xxx_free` 表，而是：**把自定义接口翻译成“带条件的资源/锁语义”，再用程序分析验证这些语义以及调用关系。** 已公开的相关工作中，LLM 主要用于补充项目特有语义，静态分析负责值流、控制流和状态检查；部分系统还引入 SMT 求解器校验路径。([arXiv][1])

你的问题需要区分三件事：

**接口识别**：这个函数到底在申请、释放、借用、转移所有权，还是加锁？

**接口配对**：某类资源允许用哪些接口归还？是否必须来自同一个内存池、设备或上下文？

**调用配对**：这一次释放的，是否就是之前申请的那个对象？在当前执行路径上，是否真的申请成功、是否仍然拥有它？

**只解决第一件事，远不足以保证后面两件事。**

## 一、先看公开工具和研究具体做了什么

这里把工业分析工具的公开机制与 LLM 研究原型分开，不能把论文中的能力直接视为所有商业 AI 代码审查工具已经具备的能力。

| 工具或研究                                    | 如何识别自定义接口                                                                                        | 配对分析依靠什么                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| **AFD：LLM 增强的分配函数识别研究**                  | 从已知分配接口出发，沿值流识别封装；让 LLM 判断某些副作用是否仅发生在错误处理路径                                                      | 改善自定义分配函数和堆对象建模，主要解决“哪些封装能按分配器建模”，不是完整资源/锁验证器。([arXiv][2]) |

从这些实现能提炼出一个适合工程落地的分工：

> **程序分析提供事实，LLM 提出语义规格，分析器检查规格与调用是否一致。**

下面展开其中最重要的部分。

## 二、如何识别自定义资源申请、释放接口？

### 1. 对普通封装：从已知原语出发，沿值流向外推导

假设底层已经知道 `malloc/free` 的语义，项目里有这样的封装链：

```text
malloc → OS_MemAlloc → ModuleAlloc → CreateMessage
free   ← OS_MemFree  ← ModuleFree  ← DestroyMessage
```

识别时不能只检查“调用图上能不能走到 malloc/free”，还要检查**资源值如何跨越函数边界**。

对申请函数，要确认分配结果最终到达哪里：返回值、输出参数、结构体成员，还是全局容器；在返回前有没有被释放或替换。

对释放函数，要确认释放目标究竟是入参本身、入参指向的对象，还是对象的某个成员。`free(obj->buffer)` 并不能推导出“这个函数释放了 `obj`”。

AFD 的公开实现就是从已知分配函数集合出发，分析分配结果与返回值之间的传播关系，迭代扩展可识别的封装，并额外处理副作用问题。([arXiv][2])

因此，下列两个判断都不成立：

```text
函数内部出现 malloc  ⇒  这个函数是对外提供资源的申请接口
函数内部出现 free    ⇒  这个函数会释放传入的资源
```

例如，一个函数申请临时缓冲区、使用后自行释放，对调用者就没有新增所有权义务。

**对 Z-Scope，这部分应优先由确定性分析完成，而不是每次交给 LLM 重新猜测。**

### 2. 对复杂接口：LLM 补充“操作意图”，但必须落到对象和条件

困难的通常是这些情况：

```c
int    BufferObtain(Pool *pool, size_t size, Buffer **out);
void   ObjectPut(Object *obj);
Handle SessionStart(Context *ctx);
int    SubmitMessage(Queue *q, Message *msg);
```

仅凭签名，无法可靠判断：

`ObjectPut` 是减少引用计数，还是把对象放进容器？

`SubmitMessage` 是借用消息、复制消息，还是成功后接管消息所有权？

`BufferObtain` 返回的是独立分配对象，还是池中一个暂借的槽位？

这时适合让 LLM 结合函数体、相关结构体、被调函数摘要、代表性调用点、错误处理分支和注释，提出**候选语义**。MemHint 就明确使用函数签名、函数体及部分被调函数代码生成结构化摘要。([arXiv][1])

但需要的输出不应只是：

```json
{"function": "ObjectPut", "role": "free"}
```

而应至少能表达：

```text
作用对象：arg0
操作：减少一个引用
触发销毁条件：引用计数变为 0
调用者义务：交还自己持有的一个引用
对象存活状态：不一定立即死亡
```

**“释放一个引用”和“释放对象内存”是不同事件。** 将两者混为一谈，容易同时制造误报和漏报。

### 3. 对没有已知底层原语的接口：需要明确的模型起点

假设内存池从静态数组中取出一个槽位，归还时只修改位图，全程不调用 `malloc/free`。

那么，“从 malloc/free 向外传播”必然无法覆盖它。对这种情况，我建议采用两步：

先由结构、调用习惯和 LLM 发现“这是资源获取/归还协议”的候选；然后由实现校验、开发者确认或项目已有契约，建立可信的底层模型。

调用点中经常出现的 `Obtain/Return`、`Create/Destroy` 组合，可以用于发现候选，但不能直接当作证明：**被分析的调用代码本身就可能存在错误。**

如果只有一个外部声明，既没有实现，也没有可靠契约，分析器应明确保留“语义未知”，而不是根据函数名补成确定事实。Clang 的自定义所有权标注机制，正是为分析器看不到实现时提供显式行为模型。([Clang][4])

## 三、接口之间如何确定配对？不是建立一对一函数表

我建议把“配对”表达成以下四项的兼容关系：

**资源种类、资源所属域、作用对象、状态转移。**

例如，下面是假设的一组接口契约，属于规格表达示意，不是某个工具的现成配置：

```text
BufGet(pool, out)
    ret == 0：
        获取 *out 的所有权
        resource_family = buffer
        resource_domain = pool

BufPut(pool, p)
    前置条件：
        调用者拥有 p
        p 来自这个 pool
    ret == 0：
        归还 p
    ret != 0：
        调用者仍然拥有 p

TryEnter(ctx)
    ret == 1：
        当前线程独占持有 ctx->mutex

Leave(ctx)
    前置条件：
        当前线程独占持有 ctx->mutex
    效果：
        释放该锁
```

在这组契约下，以下代码即使接口名称“配对”，仍然是错误的：

```c
BufGet(pool_a, &p);
BufPut(pool_b, p);     /* 资源所属池不匹配 */
```

这里为了突出问题省略了成功检查；真实分析还必须检查返回值。

另一个容易忽略的情况是：

```c
CreateObject(&obj);    /* 创建对象，同时获取对象内部的其他资源 */
free(obj);            /* 只释放外层内存 */
```

外层内存释放成功，不代表内部资源义务已经完成。因此，复杂对象的析构模型需要描述它释放了哪些子资源，而不只是“这是一个 free 类函数”。

这也意味着，正确的数据结构通常不是：

```text
一个申请函数 → 唯一一个释放函数
```

而更接近：

```text
一组获取操作
    → 某种资源及其所有权义务
    → 一组满足条件的归还/转移操作
```

同一种资源可能有多个创建接口、多个合法销毁接口；一次批量清理也可能解除多个对象的义务。**配对关系是协议关系，不一定是函数之间的一对一关系。**

## 四、最关键的正确性问题：`may-release` 不能冒充 `must-release`

这是接入 LLM 时尤其需要设防的地方。

看一个例子：

```c
void MaybeFree(void *p, int should_free)
{
    if (should_free)
        free(p);
}

void Demo(void)
{
    void *p = malloc(64);
    if (p == NULL)
        return;

    MaybeFree(p, 0);
}
```

LLM 将 `MaybeFree` 识别为“具有释放作用的函数”，这个判断并不完全错。

但如果分析器把它建模成：

```text
调用 MaybeFree(p, ...) 后，p 已经释放
```

就会漏掉 `Demo` 中的泄漏。

正确的摘要应该保留条件：

```text
should_free != 0  →  必然释放 p
should_free == 0  →  不释放 p
```

这里必须区分：

| 判断                           | 实际含义                      | 能否直接用于消除调用者的释放义务 |
| ---------------------------- | ------------------------- | ---------------- |
| **may-release**              | 某些可行执行会释放                 | 不能               |
| **must-release under guard** | 在给定前置条件和条件表达式下，相关返回路径都会释放 | 调用点证明满足条件后，才可以   |
| **unknown**                  | 当前模型不足以判断                 | 不能当作已释放          |

尤其需要警惕“用了 Z3，所以语义一定正确”的推断。

例如，MemHint 论文的摘要验证步骤明确检查“是否**存在**可行路径发生所声称的分配或释放”。这能够排除完全不可能发生的操作；但从逻辑上说，**存在性检查本身不等于无条件必然性证明**。要处理条件释放，还需要看后续摘要如何编码和消费这些条件。([arXiv][1])

因此，对 Z-Scope，我会把下面这条作为硬性规则：

> **只有经过验证的必然效果，才能在满足前置条件的调用点消除资源义务。可能效果必须分支处理，未知效果不能默认为安全。**

## 五、接口模型正确后，如何验证具体调用的配对？

### 1. 跟踪对象身份，而不是变量名或调用次数

看下面两段代码：

```c
p = MyAlloc();
q = p;
MyFree(q);            /* 可能完全正确：q 与 p 指向同一对象 */
```

```c
p = MyAlloc();
q = MyAlloc();
MyFree(q);            /* 释放了 q，并没有释放 p */
```

真正需要跟踪的是“对象”，而不是 `p`、`q` 这两个名字。

在实现上，需要将赋值、参数传递、返回值、字段访问和指针派生联系起来；还需要避免把同一分配函数在不同调用点产生的对象过度合并。AFD 的研究就专门讨论了自定义分配封装导致堆对象建模过粗、不同调用结果被错误视为别名的问题。([arXiv][2])

对你使用的 SVF 一类指针分析结果，特别要区分：

**可能别名**只能说明两个值存在指向同一对象的可能，不能直接证明“这次释放必然释放了目标对象”。需要结合当前路径进一步细化。

### 2. 沿路径跟踪状态，而不是数申请与释放次数

可以把最简单的独占所有权协议理解为：

```text
未获取 → 已拥有 → 已释放
                ↘ 所有权已转移
```

在这个模型下，释放后再次释放、释放后继续访问、释放不属于自己的对象，都是不同的非法状态转移。

但“函数返回时没有释放”不一定是泄漏：函数可能把对象通过返回值或输出参数交给调用者，也可能交给一个明确接管所有权的容器。Clang 特意用不同的所有权属性区分直接释放与接管后延迟释放，就是为了表达这种差异。([Clang][4])

需要坚持两个边界：

**逃逸不等于已释放。** 对象被放入某个全局结构，只是改变了可达性，不自动证明后续会正确清理。

**所有权转移不等于义务消失。** 它只是把清理义务转交给另一个主体；局部分析可以结束当前函数的义务，全局分析仍需检查接收方。

### 3. 跨函数关联条件，并检查路径可行性

例如：

```text
Create 成功
    → 初始化第二个子资源失败
    → 跳到错误清理分支
    → 调用 Cleanup
    → 返回
```

是否存在泄漏，取决于 `Cleanup` 在这个具体状态下清理了哪些资源，而不是调用图中有没有一个名字像 cleanup 的函数。

跨函数分析可以选择内联、函数摘要，或两者结合。Clang Static Analyzer 的公开实现支持分析时内联，但也明确存在调用深度、函数体可用性和分析预算等限制。([Clang][6])

对需要高置信度的告警，我建议输出可以复查的证据链：

```text
获取事件
→ 成功条件
→ 对象传播
→ 所有权变化
→ 清理调用及其条件
→ 最终违反的协议
```

SMT 可以帮助判断这条路径的约束是否矛盾，但**求解器只保证它收到的公式的求解结果**。如果宏配置、整数语义、别名关系或被调函数摘要翻译错了，求解过程再严格也无法修复这些错误。

## 六、锁比普通资源配对多了哪些约束？

自定义锁接口同样可以向下追踪到底层同步原语，但最终模型不能只保存 `lock/unlock` 标签。

| 维度         | 需要表达的内容                            |
| ---------- | ---------------------------------- |
| **锁对象身份**  | 锁的是 `ctx->mutex`、全局锁，还是通过句柄解析出的某把锁 |
| **获取条件**   | 无条件获取、尝试获取、超时获取；哪种返回值代表成功          |
| **持有模式**   | 独占、共享，以及是否允许递归获取                   |
| **持有主体**   | 当前线程、任务或特定执行上下文；是否具有所有者约束          |
| **附加状态**   | 是否保存/恢复中断状态，是否存在配套的状态令牌            |
| **过程中的效果** | 是否曾临时解锁，即使返回时又恢复了持锁状态              |

Clang 的锁属性区分共享、独占和尝试获取，`TRY_ACQUIRE` 还需要明确成功返回值。Linux 的锁文档则明确区分所有者语义：计数信号量不能直接套用普通互斥锁的“谁获取、谁释放”规则，中断状态保存/恢复也有额外语义。([Clang][5])

这里有两个值得你特别关注的坑。

### 坑一：同一个字段名，不代表同一把锁

```c
MyLock(&a->mutex);
MyUnlock(&b->mutex);
```

必须证明 `a`、`b` 在这条路径上对应同一个对象，才能确认配对。两个对象的字段都叫 `mutex` 没有意义。

而且不能假设所有现成锁分析器都自动解决了这个问题。Clang 官方文档明确说明，其线程安全分析不做通用指针别名分析，也不会通过内联自动推导被调函数的锁效果，而是依赖声明的属性。([Clang][5])

### 坑二：入口和出口都持锁，不代表中间没有释放

例如：

```c
void Helper(Context *ctx)
{
    MyUnlock(&ctx->mutex);
    DoSomething();
    MyLock(&ctx->mutex);
}
```

如果摘要只记录：

```text
进入：持锁
退出：持锁
净变化：0
```

就丢失了“中间临时解锁”的重要事实。调用者原本以为受锁保护的不变量，可能已经在中途失效。

Linux lockdep 的 pin/unpin 机制就专门关注这类“上层要求持续持锁，但下层释放后又重新获取”的情况。([Linux内核文档][7])

所以，我建议锁摘要除了前后状态，还保留 `may_temporarily_unlock` 或更精确的有序效果。

另外，**锁都成对释放，也不代表没有死锁**。一个执行上下文按 A→B 获取，另一个按 B→A 获取，即使各自最终都有对应 unlock，仍然需要单独检查锁依赖环。lockdep 的锁顺序分析就是另一层检查。([Linux内核文档][7])

## 七、放到 Z-Scope，应该怎样建设这层能力？

我的建议是：把它做成一个**扫描前可缓存、可版本化的资源与锁规格层**，而不是每个入口分析时都让 Agent 临时判断一次。

### 第一层：发现与建模

确定性分析先处理已知原语、普通封装和明确的值流映射；LLM 只处理未决语义、复杂资源协议和候选关系。

摘要至少应保存：

```text
接口身份：真实符号 + 所属构建/链接目标
作用位置：return、*arg、arg->field 等
资源类别与资源所属域
前置条件、成功条件、失败效果
获取/释放/借用/转移/引用计数/锁操作
may 或 must，以及 must 成立的条件
证据位置、依赖的其他摘要、验证状态
```

同名函数不能只按名字合并；摘要缓存也不应只依赖函数名。函数体、宏配置或被依赖摘要变化时，应触发相关模型失效和重新验证。

### 第二层：验证规格，再验证调用

这两种验证必须分开：

**规格验证**回答“`BufPut` 是否真的在指定条件下归还了指定对象”。

**调用验证**回答“这个调用点是否满足 `BufPut` 的前置条件，以及它归还的是不是目标资源”。

LLM 生成的规格应先保持 `proposed`。通过程序证据校验后再升级；依赖人工契约的模型，应明确记录为“基于该契约的假设”，而不是冒充已经从实现证明。

尤其不要让另一个 LLM 简单复述“我同意”，就把规格升级成已证明。

### 第三层：反例回放与协议测试

对资源问题，可用 ASan 检查释放后使用、重复释放等具体执行错误，用 LSan 检查内存泄漏；TSan 的主要职责是数据竞争检测，不应被当作全部资源与锁协议的通用验证器。([Clang][8])

对自定义内存池，我更建议补充接口级事件探针，例如记录：

```text
资源实例、所属池、获取/归还事件、线程、调用位置
```

这样即使底层没有发生真正的 `free`，也可以检查“逻辑资源有没有归还”。

同时，给每类模型建立小型反例集：错池归还、释放另一个对象、获取失败后释放、条件释放未满足、所有权已经转移、错误线程解锁等。模型应当既识别正确用法，也能稳定拒绝这些错误用法。

---

**最终能提供的可靠保证，应是“在明确的构建、接口契约和分析范围内，该配对关系已经验证”，而不是“接入了 LLM，所以任意自定义接口都能自动正确配对”。**

对 Z-Scope 而言，最有价值的建设顺序是：

**可信原语模型 → 带条件的接口摘要 → 资源实例与所有权跟踪 → 路径及协议验证。**

LLM 的价值在于减少“项目特有语义无人建模”的盲区；真正防止误配的关键，则是**同一对象、同一资源域、正确条件，以及合法的状态转移**。
