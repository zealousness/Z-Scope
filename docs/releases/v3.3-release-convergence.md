# Candidate schema v3.3 convergence (Z-SCOPE v1.3.1)

## Scope

Internal schema v3.3 closes deterministic evidence before LLM validation, projects structurally
equivalent obligations through `FindingRoot v1`, and bounds Validator context and
turns without treating time, token, or request limits as hard analysis budgets.
Range truth is used only by the offline evaluator and is not available to runtime
detectors, proof providers, grouping, or validation.

The release candidate is gated by all of the following on every formal cold run:

- complete, valid scan with 88/88 discovered entries and GLM-5.1 in API traces;
- confirmed TP >= 85 and raw actionable precision >= 95%;
- with-review TP >= 134, raw FP <= 100, and needs-review <= 150;
- total model tokens <= 6,000,000 and scan wall time <= 3,600 seconds;
- drained validation queue, zero pending/not-completed/deferred-budget candidates,
  observe-only budget policy, and valid report invariants.

The benchmark runner writes the evaluated checks and blockers to
`release_gate_status` in both `run_summary.json` and the JSON report. A completed
scan that misses a release threshold remains a valid benchmark artifact but the
release runner exits with code 2.

## Contract and cache isolation

The release upgrades these internal contracts:

- `zscope.decision-facts.v1.2`
- `zscope.security-obligation.v1.2`
- `zscope.decision-context.v3.3`
- `zscope.candidate.v3.3`
- `zscope.decision-proof.v4`
- `validator-contract.v6`
- `zscope.validator-evidence-slice.v2`
- `zscope.validator-protocol.v2`

Schema v3.2 candidate, proof, grouping, outcome, and Validator caches are intentionally
incompatible and must not be migrated. Raw occurrences, entry identities, call
paths, and provenance remain available in reports using schema v3.3.

## Feature flags and activation order

The release behavior remains reversible through additive analysis flags:

1. `proof_providers_v12`
2. `decision_context_v33`
3. `finding_root_v1`
4. `validator_evidence_slice_v2`

The Range release configuration enables all four. `ValidatorEvidenceSlice v2`
sends one canonical occurrence, one representative entry path, structured decision
facts, and exact code slices. Aliases are represented by counts and a stable UID
commitment. The Validator has no broad browsing tools and may produce at most an
initial answer plus one JSON repair response; protocol exhaustion becomes a
canonical `needs_review`, not an engine failure.

`FindingRoot v1` only aliases obligations with the same defect family, structural
subject, decision region, dependency code, and proof context. Different fields,
guards, paths, locks, ownership, or revisions remain separate. Alias occurrences
and affected subjects are retained for audit.

## Migration

1. Stop or finish all schema-v3.2 scans before changing the default flags.
2. Preserve schema-v3.2 reports and caches for one release cycle as rollback artifacts.
3. Start schema v3.3 with empty snapshot, KnowledgeDB, validation, proof, and outcome
   cache directories.
4. Confirm the report manifest identifies `zscope.candidate.v3.3`, uses the
   observe-only budget policy, and reports a drained validation queue.
5. Do not resume a schema-v3.3 scan from a schema-v3.2 report; compatibility checks reject
   the old candidate contract.

## Rollback

Disable the four schema-v3.3 flags together and restore the previous application version and
its preserved cache directory. Never point schema v3.2 and v3.3 at the same validation or
outcome cache. Reports already emitted with schema v3.3 remain readable through public
report schema version 2; the new fields are additive.

### Remaining production-release obligation

This repository contains the Range development truth set but no anonymous sealed
or holdout set. Consequently the required sealed-set quality regression check
(no more than two percentage points) cannot be executed locally. The Range gate
is fully passed, but production release approval remains conditional on the
external sealed-set run. A missing sealed-set result must not be represented as a
pass.
