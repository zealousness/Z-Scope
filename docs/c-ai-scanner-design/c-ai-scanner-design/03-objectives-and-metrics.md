# 03 · 预期目标与度量

[返回文档导航](README.md) · [能力地图](01-capability-map.md) · [设计架构](02-design-architecture.md) · [实施路线](04-delivery-roadmap.md)

> 本文描述待验证的产品目标与评价口径，不提供尚不存在的实测结果。98% 来自原方案的拟定目标；召回率和性能的绝对数值需通过基准建立，不能仅从架构推断。

## 1. 优化顺序

目标不是三个指标任意加权，而是按优先级约束优化：

```text
先使正式报告达到约定精确率门槛；
在该门槛下最大化最终缺陷召回；
在质量与覆盖不回退的条件下优化耗时、资源与人工成本。
```

候选发现允许宽松，正式确认严格。候选积压、条件性结果与覆盖缺口必须显式呈现，不能用少报、不处理难例来实现表面上的高精确率。

## 2. 预期目标表

| 维度 | 预期目标 | 性质与验证方式 |
| --- | --- | --- |
| 正式报告精确率 | 初期拟以 **≥98%** 为产品目标 | 待评测校准；按根因去重，披露样本量、未裁定率与统计不确定性；不是保证 |
| CI 自动阻断 | 比普通报告更严格，并按缺陷类别校准 | 可选能力；不因进入正式报告就自动阻断，不预设未经验证的更高百分比 |
| 最终召回率 | 在精确率达标条件下持续提高，不以候选数代替 | 以已知真缺陷基准为分母，分类型及总体报告；先建立基线再约定绝对目标 |
| 复杂缺陷覆盖 | 从基础内存问题扩展到自定义资源、异步生命周期和协议错误 | 使用能力地图及分阶段测试集验收，不声称首版覆盖全部 C 环境 |
| 报告证据完整性 | 正式报告均有构建范围、关键事实、前提、见证与源码位置 | 结构完整性检查；字段存在不等于证据真实，仍需语义审核 |
| 未知处理 | 不把超时、未复现、未知契约或未支持语义自动判为安全 | 使用专门反例测试与状态变更记录检查 |
| 分析覆盖 | 所有输入范围、失败和限制可说明；支持范围内失败不从召回分母消失 | 报告构建、解析、调用、模型和事件覆盖 |
| 增量一致性 | 在规定回归集、相同配置与预算下，增量与全量的结论和覆盖无非预期差异 | 对照扫描；不据此承诺任意程序零漏报 |
| 扫描性能 | 在同等质量与覆盖下改善冷启动、重复全量与增量成本 | 报告端到端时间、分阶段耗时、内存和 LLM 成本；暂不承诺百万行耗时 |
| 人工成本 | 降低每条确认缺陷的复核与定位成本 | 记录人工复核时长、补充信息次数及复现材料可用性 |

未确定的绝对指标应在基线建立后填写，不能用“行业经验”虚构百分比或速度目标。

## 3. 评价对象与统计单位

### 3.1 按缺陷根因，而不是告警条数

同一根因由多个工具、多个调用点或多个相似执行见证重复报告，只计一个被发现缺陷。报告与标注真值的匹配规则在评价前确定，避免通过随意合并或拆分操纵指标。

不同对象、独立根因或不同责任错误不能仅因报错行相同而合并。

### 3.2 固定范围，显式记录支持边界

每轮评价固定代码版本、构建目标、配置、目标平台、契约集、工具版本和资源预算，并记录 LLM 版本与重复运行条件。

在声明支持的范围内，已知缺陷因解析失败、间接调用未知、验证超时或预算不足没有被正式报告，均属于最终召回中的漏报。真正不在声明支持范围内的样本可以单列，但不能在看见结果后临时缩小范围。

## 4. 精确率与误报

定义：

```text
TP：已正式报告，且经评价确认真实的缺陷根因数。
FP：已正式报告，且经评价确认不成立的缺陷根因数。
FN：基准中的真实缺陷，未得到正确正式报告的根因数。
U ：已正式报告，但尚未完成人工或独立真值裁定的根因数。
```

在标签完整时：

```text
Precision = TP / (TP + FP)
告警误报占比 = FP / (TP + FP) = 1 - Precision
```

主要关注“开发者收到的报告有多少不是真的”，不以庞大的正常代码量作为分母制造很低的传统假阳性率。

当 `TP + FP = 0` 时，精确率应记为不适用，不能写为 100%。没有任何报告也不意味着达到低误报产品目标。

存在未裁定报告时，须同时展示 `U` 及其比例。仅在已裁定子集上计算的高精确率不能冒充全部报告精确率。评测结果同时披露样本量与置信区间或其他明确的不确定性说明。

按内存越界、空指针、UAF、double free、数据竞争、并发回收等类型分别统计；总体达标不能掩盖某一类别明显失真。

## 5. 召回：区分发现能力与确认能力

```text
最终召回率 R_final = TP / (TP + FN)

候选召回率 R_candidate = 已产生对应候选的真实缺陷数 / 基准真实缺陷数

候选确认率 R_confirm_given_found
  = 获得正确正式报告的真实缺陷数 / 已产生对应候选的真实缺陷数
```

所有发现通道进入统一候选流程、且统计单位与范围一致时：

```text
R_final = R_candidate × R_confirm_given_found
```

据此定位研发投入：

| 现象 | 主要投入方向 |
| --- | --- |
| 候选召回低 | 补入口与事件覆盖、缺陷发现机制、AI 对象级主动探索 |
| 候选召回高，正式召回低 | 补别名/路径验证、项目契约、并发模型与合法复现能力 |
| 大量候选被同一未知接口阻塞 | 优先建模公共接口，避免逐条重复审查 |
| 正式精确率降低 | 复核抽象精度、见证具体化、环境假设与报告条件 |

真实缺陷留在条件性或待验证状态，不计入主要正式召回的 TP。可另报“已发现但未确认”的数量，但不能用它替代最终交付成果。

## 6. 必须同时报告的辅助指标

| 类别 | 建议指标 | 用途 |
| --- | --- | --- |
| 构建覆盖 | 纳入/预期的构建配置与链接目标、编译实例数 | 明确分析的是哪些程序 |
| 解析完整性 | 解析成功率、失败原因及影响范围 | 防止静默跳过难文件 |
| 语义完整性 | 未解析间接调用、未知外部接口、未建模同步原语 | 识别误报和漏报的公共来源 |
| 候选状态 | 已确认、条件性、待验证、已排除数量及主要原因 | 识别验证积压与弃权行为 |
| 证据质量 | 见证可回放率、驱动有效性、报告前提完整度 | 防止人工桩函数制造缺陷 |
| 人工成本 | 每条报告与每个真缺陷的复核时长 | 衡量开发者实际负担 |
| 调度公平性 | 主动探索完成度、长期未决候选类型 | 避免只确认易例 |

辅助指标不能单独证明正确性。例如解析成功率高，不代表别名与并发语义完整。

## 7. 性能评价口径

分别测量：

- **冷启动全量：** 从无缓存开始，包含构建导入、索引、摘要、候选、验证与报告。
- **复用式全量：** 源码未变时重复执行，检查摘要和证据缓存收益。
- **增量：** 给定真实变更，统计失效分析、重新验证与报告更新成本，并与全量对照。

记录端到端及分阶段耗时、峰值内存、CPU 使用、存储、LLM 调用次数/输入输出 token、验证器成本、每个确认缺陷的成本。重复运行可报告中位数及 P95，同时标明样本数量。

性能对比须保持目标配置、覆盖范围、精确率与召回基线一致；若出现质量变化，必须同时展示，不能只报加速倍数。

不采用以下“优化”：跳过难例却计为已扫描、降低验证标准、将预算耗尽当安全、减少配置而不披露、从耗时中删除验证或人工复核成本。

## 8. 基准集设计

| 数据集 | 作用 |
| --- | --- |
| 基础缺陷与安全样例 | 快速定位算法、契约与状态处理回归 |
| 真实项目缺陷及修复前后版本 | 验证实际构建、上下文与工程适配 |
| 复杂安全反例 | 检查不同实例、路径互斥、合法转移、引用持有和等待机制导致的伪候选 |
| 并发协议样例 | 检查同锁 UAF、回调回收、取消/完成竞争、死锁可达性与原子性 |
| 增量变更集 | 检查新增访问者、新回调、契约/宏/头文件变化导致的失效 |
| 人工构造或变异样例 | 补充边界覆盖；单独标识，不替代真实缺陷集 |

划分按项目进行，防止近重复代码同时进入调优与验收集合。基础公开集合可沿用原方案提到的 [NIST SARD/Juliet](https://samate.nist.gov/SARD/test-suites)，但不将通过合成测试等同于生产可用。

安全反例应至少覆盖：成功/失败返回导致所有权差异、同分配点不同实例、两线程实际不可并发、注销确实等待回调、按设计长期保留资源、锁顺序环的路径互斥。

## 9. AI 增益的消融实验

依次评价：

```text
纯静态发现
→ 加 AI 项目语义建模
→ 加 AI 主动探索
→ 加局部验证与动态复现
```

各组使用相同项目划分与统计口径，同时记录质量和成本变化。重点回答：AI 增加了哪些原来找不到的真缺陷，减少了哪些误报，解锁了多少未决候选，以及为这些收益增加了多少计算和人工成本。

AI 只改善报告文案，不等于提升缺陷发现或确认能力。
